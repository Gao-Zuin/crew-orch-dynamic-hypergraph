# 超图任务字段是不是实际责任表：三条砍树轨迹的影子索引

日期：2026-11-08。分析器：`analyze_target_responsibility_shadow.py`；逐提交、逐动作结果：`TARGET_RESPONSIBILITY_SHADOW_3_RUNS.json`。

## 结论先行

当前轻量超图的`edges[].tasks`不能单独充当权威责任表：

- Pro R2从初始到结束的10次图提交，都把25个目标中的每一个同时主分配给两个人；
- Flash R2的图内主分配没有碰撞，但大量实际改派发生在聊天里，最终图又因错误找水任务只剩14/25个目标有主责任人；
- Flash R3的图内主分配不碰撞，改用显式条件备用；6个由“图上非责任人”最终清完的目标都能在近期leader消息中找到坐标证据，但进一步按版本重放后，只有5个有当前有效的责任依据，另1个是旧消息已被新图覆盖后的陈旧执行。

因此，“图上非责任人做了任务”不自动等于越权。更准确的问题是：**实际责任状态分散在图任务、leader消息和环境完成证据三处，没有一个可直接查询的合并视图。**

## 方法边界

范围是同一`Cut_Trees_Sparse_large / seed42`的三条完整轨迹。对全部26次`TASK_GRAPH_COMMITTED`：

1. 只有以`Cut`或`Continue cutting`开头的任务文本才产生目标所有权；普通侦察坐标不算。
2. 带`if / only if / otherwise / fallback / assist / ownership caveat`的任务记为条件责任，不升级为主责任。
3. 实际移动只有精确指向25个任务坐标才纳入；砍树使用动作前真实位置。
4. 完成要求`ACTION_COMPLETED`中当前格树数真实降至0。
5. 对图上非责任人的动作，再检查此前5步实际送达给该人的消息是否同时包含该坐标与分配/接管语言。

近期消息只是候选“改派证据”，不自动证明发送者有最终权限，也没有比较消息和后续图提交的版本先后。自然语言解析采用保守规则，逐动作明细保留在JSON中。后续版本化重放见[责任事件账本审计](RESPONSIBILITY_EVENT_LEDGER_AUDIT_20261108.md)，它修正了本报告仅靠近邻消息形成的一个过宽结论。

## 图本身的责任结构

|轨迹|图提交|存在主责任碰撞的提交|一次最多碰撞目标|存在主责＋条件备用重叠|终局主责覆盖|
|---|---:|---:|---:|---:|---:|
|HT-R2 Flash|12|0|0|0|14/25|
|HT-R2 Pro|10|10|25|0|25/25|
|HT-R3 Flash|4|0|0|4|25/25|

### R2 Pro：不是偶发重复，而是初始设计就双重覆盖

Pro把25个目标分成5组，每组5个坐标，然后将同一组完整复制给两名不同成员。例如1号和6号收到同一组五个目标，4号和9号收到另一组五个目标。10次图提交都保留这一结构，因此25/25目标始终有两个“主责任人”，没有主备区别或释放条件。

这会让“是否遵守图上任务”失去判别力：两个人都可以声称自己是合法主责，重复旅行和重复砍空格仍可能发生。该轨迹共有37次任务坐标上的无效果砍树。

### R2 Flash：图内无冲突，但责任迁移发生在图外

初始图给10名成员划分了互不重复的目标。随后成员和leader在组内聊天里大量交换、接管和释放坐标，但多数没有触发图任务更新。后期错误水资源瓶颈又使四名西北组成员改成找水，终局只有14个任务坐标仍出现在主责字段中。

所以它的图看起来“零冲突”，并不意味着实际责任清楚；只是冲突和接管已移到消息层。

### R3 Flash：条件备用比双主责更合理

R3四次图提交都没有双主责，但保留1—2个“主责＋条件备用”重叠。例如8号只有在team A未处理`(21,42)`时才能接管。这比Pro的双主责更清楚，因为它至少表达了接管条件。

问题是条件是否满足仍靠聊天和模型判断，没有由环境完成状态自动激活或关闭。

## 图任务与实际行动的偏离

|轨迹|指向任务坐标的动作|图上其他主责人的动作|其中有近期改派消息|由其他主责人最终清空|其中有近期改派消息|无效果砍树|
|---|---:|---:|---:|---:|---:|---:|
|HT-R2 Flash|332|140|129|11|9|34|
|HT-R2 Pro|495|157|117|5|4|37|
|HT-R3 Flash|153|53|53|6|6|3|

这些动作不是独立样本，连续多步移动会重复出现。更重要的是，“其他主责人”只是相对图字段而言，不能直接叫违规。

R3的6个非图主责完成分别是8号清`(28,24)`、10号清`(22,50)/(26,44)`、2号清`(19,37)`、8号清`(20,49)`、3号清`(12,31)`。它们都能在近邻窗口里找到leader消息，但按完整时间顺序重放后不能一概视为合理接管：其中4个已由当前组leader正式改派，1个`(28,24)`是有明确现场意图但尚未获原组释放的跨组暂定接管；2号的`(19,37)`则在step 4收到旧指令后，于step 5被新图改派给6号，2号仍在step 7执行，是应被捕获的陈旧责任冲突。

R2 Flash中则存在真正冲突反例：6号从step7起反复声明自己占用`(26,44)`，leader 5也确认6号负责该点；8号仍在step15完成该点，且近5步没有释放或改派消息。另一个`(9,40)`接管来自较宽泛的“转去南组/西部目标”释放，说明仅靠精确坐标消息也会漏掉合法范围级接管。

## 对本地超图价值的修正

动态超图的优势不能表述成“图里写了分工，所以责任明确”。三条轨迹显示：

- 静态主责可以避免初始重复，但很快会被现场改派超越；
- 显式条件备用优于无条件双主责；
- 真正有效的R3协作主要依靠leader消息更新责任，并由环境树数验证完成；
- 如果强制成员只能做图上任务，会错误阻止5次有效或有明确意图的接管；如果只检查“最近是否出现过授权消息”，又会漏掉`(19,37)`这种被更新图覆盖的旧授权。

因此更合适的定位是：超图提供**关系和初始责任范围**，而不是独占的执行真相。

## 下一层设计

需要的不是每次聊天都重建整张超图，而是一个小型派生索引：

`target → primary owner → conditional backup → assignment source/version → environment status → released/completed`

更新来源分三层：

1. 图提交建立或重置主责；
2. 结构化leader改派事件更新当前owner或激活backup；
3. 环境树数到0自动关闭目标，避免重复砍空格。

对不在索引中的临时接管，不应直接禁止，而应要求显式`claim/release`或记录为影子异常。这样既能保留R3的有效现场调度，也能捕获R2 Flash的`(26,44)`争用和Pro的全目标双主责。

## 价值与创新性判断

### 已有价值

- 区分了三种常被混为一谈的现象：双主责、条件备用、消息改派。
- 找到R3的5个有效或暂定接管正例和1个陈旧执行反例，防止设计出“只服从图”或“见过授权就永久有效”两种错误门禁。
- 把无效果砍树从37/34降到R3的3，与更清楚的分工和完成验证同时对齐。

### 仍不构成创新

目标预留表、合同网、黑板和版本化任务分配都是已有思想。仅增加`target_owner`字典不是研究贡献。

### 可能形成贡献的部分

有潜力的是：在动态超图中把**关系拓扑**与**可恢复责任事件**分离，用环境证据自动完成/释放，再通过影子重放先测“会阻止多少有效接管、捕获多少真实争用”。论文价值取决于后续受控实验能否同时降低重复动作、保持新事件响应速度，并提高固定时域AUC；不能只展示索引更整齐。

## 下一步门槛

先在冻结轨迹上实现高精度的结构化`ASSIGN / CLAIM / RELEASE / COMPLETE`派生事件，只处理明确leader指令和环境完成，不从宽泛聊天强猜。用R3的5个当前有效/暂定接管作正对照，用R3`(19,37)`和R2 Flash`(26,44)`作必须捕获的负对照。通过后再做一个短砍树Unity实验，不直接改正式五任务运行时。

## 限制

- 任务与消息仍是自由文本，解析器只覆盖高精度形式。
- 多树格允许多人连续有效砍树；“非主责”不等同于浪费。
- 近5步消息证据不证明权限，只证明图外责任信息存在。
- 本报告的近邻窗口没有实现版本优先级；关于“六个均有效”的原结论已由后续事件账本修正。
- 三条轨迹版本不同，不能把无效果动作下降完全归因于责任机制。
