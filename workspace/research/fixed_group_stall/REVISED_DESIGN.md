# 对齐原完整任务阶段超图的修订设计

2026-10-23：核对后确认，原有实现是 `TaskHypergraph` + `LLMTaskPolicy`，支持完成检查、超边退役、后继边、责任交接、重叠成员和跨边路由；当前运行路径后来改接轻量 `SoftTaskGraph`。此前的 `PROTOCOL.md` 和两步门禁只验证轻量路径，不能当作原完整超图的固定组织实验。

## 场景

可以把两个子任务放在**同一个 Unity 世界**里，而不是把两个独立 level 的日志或回报拼接。首选现有的 `Suppress_Fire_Extinguish_Second_Fire`：原火点任务运行中出现第二火点，旧边是否仍适配、新火点是否有人负责、资源和成员如何重新分配，都有可核查的环境事件。已有真实轨迹出现过事件后超边重组和跨边送达，但仍未证明压制收益。

若要更强的串行阶段依赖，可在 `Full_Game` 上制作独立诊断场景：同一世界保留消防、无人机、直升机和平民，第一阶段有救援/灭火工作；在预先指定且经世界状态确认的里程碑后注入第二处火或新一批平民，迫使已有人员/运力重新分配。注入条件和目标数必须在运行前固定，动作后世界快照需证实事件真的发生。不能只在 prompt 中宣布新任务。`Full_Game` 原 validator 只看火是否消失，需另设组合里程碑和完整成功判据，并阻止原 validator 在其他目标未完成时提前结束。所有结果标为新诊断场景，不混入官方任务成绩。

## 组织对照

使用**同一套原有 `TaskHypergraph`、组织提案/独立审查、动作、通信和记忆规则**。固定臂在任务开始时形成超边，此后允许阶段检查、目标/任务修订和有证据的责任交接，但约束成员关系；动态臂在同样信息和预算下允许原组织器提出成员变化。动态臂选择不变也保留为结果。固定约束如何处理后继边、死亡成员与重叠成员，必须先在原图状态机中明确定义并通过审计，不能通过替换为轻量图来实现。

人工指定一次换成员只适合后续**诊断上界**：它回答“这个卡点若改成员，是否可能解除瓶颈”，不能代表原超图的自动重组能力。首轮主比较应观察原有动态组织器是否在真实事件后改组，以及改组是否改变世界进展；若要配对分支，当前 Unity 无完整检查点，必须核对重跑前缀并如实标记非同状态近似比较。

## 开跑前门禁

1. 从既有冻结源码恢复原完整任务阶段超图运行路径，并保持旧结果与新结果版本分离。
2. 检查组合场景的物理事件、目标计数、完成判据和提前退出逻辑。
3. 对固定约束、原动态臂分别做短 Unity 门禁；审计完成检查、责任交接、动作归属和消息路由。
4. 冻结任务、seed、阶段事件、卡点阈值、预算和源码后再启动正式运行。
