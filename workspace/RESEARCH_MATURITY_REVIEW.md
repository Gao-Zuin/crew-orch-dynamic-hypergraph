# CREW 超图协作研究：现象、机制与下一步问题

2026-10-11

## 1. 核心判断

现有实验将问题集中到了一个具体环节：**正确事实怎样经过通信与决策，转化为经过环境确认的任务进展。**

超图适配已经提供版本化状态、局部 context 和分组路由。轨迹显示，这些机制能帮助成员发现错误完成声明，也会与不可行计划、信息采用失败和执行拖延同时存在。因此，当前研究的中心应从“组织了多少通信”转向“组织如何改善证据到行动的闭环”。

下文先提炼四项证据链较完整的现象，再分析尚未解释的机制，最后确定可迁移部分与后续研究路径。

## 2. 四项值得保留的现象与结论

### 2.1 正确保存事实与正确使用事实，是两个独立环节

普通 Embodied 的一条灭火轨迹中，原始观测和 perception 摘要都报告水量为 0，通信却宣称已经补满。后续行动理由引用了这个完成状态，agent 离开水源，下一步水量仍为 0。错误发生在从观测到通信、再到行动的过程中，而非最初读取观测时。

加入结构化状态后，另一类轨迹出现了有效纠错：直升机宣布完成卸载，成员根据仍在机上的实际人数提出纠正，直升机返回执行卸载。

但 HR 中也反复出现容量死锁。直升机已经载了 5 人，状态和推理都保留了这个正确数字，却坚持等待第 6 人上机后才出发，而容量只有 5。

这三种轨迹区分出三个研究对象：

1. **事实保存**：公共状态是否被错误声明覆盖。
2. **事实采用**：决策是否依据当前证据，而非旧消息或自己的承诺。
3. **计划可行性**：依据这些事实选出的行动序列是否能够完成。

当前 ledger 主要处理第一项，局部 context 影响第二项，第三项仍由 agent 规划承担。容量死锁说明，增加事实提示后，下一步要测量的是 agent 如何使用事实，以及何时据此放弃原计划。

### 2.2 消息投递减少与端到端效率，可以朝相反方向变化

在 v3 扩展批次中，HR 相对 HA 的接收者级消息投递减少约 42.2%，返回 token 增加约 7.3%。运输 seed 7622 中，HR 最后完成 0/6，HA 在 10 步完成，关闭状态提示的 HR-off 在 8 步完成。

v2 中 HR 的 token 则低于 HA。两个批次呈现不同方向，使“通信抑制如何影响总成本”成为需要解释的问题。

总开销由多项组成：状态提示、通信内容、感知与行动推理、历史增长，以及运行轮数。路由直接降低的是部分消息投递；它同时可能改变信息获取、决策和完成时间。

**这组结果支持将通信节约与任务效率分开测量。** 后续比较需要将总 token 拆到各类调用，并检查额外轮次发生在什么任务状态。这样才能分清提示开销、重复协调和推进缓慢各自的贡献。

### 2.3 协作停滞发生在“送达之后”和“到达之后”

一条运输轨迹中，成员提出“先送现有乘客，再回来接最后一人”，消息已经送到 leader。leader 后续仍要求全员上机才出发。链路完成了投递，决策没有采用建议。

另一条运输轨迹则成功卸载了首批 5 人，随后直升机与最后一名消防员反复调整会合地点。接上最后一人并到达目标时，行动预算已经用完，乘客仍在机上。

这两类停滞分别发生在：

> 证据可用 → 信息送达 → 计划更新 → 相关动作 → 后置条件确认

前一类停在信息采用，后一类涉及会合效率和末端执行。只记录投递成功、最终人数或总耗时，会把它们混为同一种失败。

**协调质量需要按上述链路分段评价。** 其中最有价值的是：正确证据出现后多久产生相关行动，以及预算内未产生响应的比例。

### 2.4 活动量与任务结果，需要由世界状态连接起来

树线 seed 4881 中，P 新增砍树数 119，有效清理分数最终为 27/30；HR 新增砍树数 86，却完成了 30/30。初始有效分数为 13，所以两者新增有效进度分别为 14 和 17。动作量差异只有结合目标位置，才能解释为任务贡献。

灭火还暴露了评分条件的问题。原 validator 要求烧毁树木数大于 0，再检查无活跃火。seed 4936 中，HR 和 HR-off 已观察到起火，之后持续无活跃火，但烧毁数为 0，因此原评分为失败。

在新 seed 6216 中，HA 最后仍有活跃火；HR 最后无活跃火且通过原 validator；P 和 HR-off 也无活跃火，但因烧毁数为 0 未通过原 validator。

这些轨迹要求评价同时保留三类结果：

- **行为**：执行了什么、执行了多少。
- **任务状态**：目标完成度、起火后的火场状态、实际交付人数。
- **代价**：token、时间、烧毁损失与 agent 损毁。

原始评分和世界状态诊断应并列呈现。前者保留 benchmark 的评价口径，后者解释口径与实际任务状态之间的差异。

## 3. 目前的关键缺口：收益究竟来自哪里？

### 3.1 状态增益与组织增益混在一起

HA 同时增加了队友状态、结构化呈现、组与角色描述，并改变 prompt 长度。P→HA 的结果因此包含多个机制。

要识别组织结构的作用，需要一个中间对照：给 agent 相同的事实，但不使用超图分组与角色提示。由此把比较拆为：

> 原始 agent → 同事实状态共享 → 超图组织的状态共享

还需要记录这些事实原本如何获得：直接观察、队友消息，还是 adapter 提供。信息可获取性的改变本身就会影响任务表现。

### 3.2 路由、反馈与恢复提示共同改变了行为

HR 增加消息限制，也提供抑制反馈，并在部分运行事件发生时发送提醒。HR−HA 因而测量的是这一整套路由机制。

下一步应分别打开路由限制、投递反馈与事件提醒，观察它们对信息采用和恢复延迟的影响。HR-off 则用于研究状态提示在路由开启时的作用；动作改变后，位置和实际拓扑也会随之改变。

### 3.3 当前分组依赖空间，研究目标依赖任务

当前 policy 以空间近邻形成核心大小不超过 3 的组，按几何位置选择 leader，并添加桥接成员。它回答“谁离谁近”，而运输和救援还需要回答“谁持有资源、谁能执行、谁等待交接”。

这一差距决定了下一阶段的结构研究：比较空间邻近与任务依赖两种分组依据，检查后者是否缩短关键证据到达和任务推进的时间。

重叠结构也应在这里评价：共享 agent 是否促成了有效跨组推进，同时是否受到两个组的竞争请求。三 agent 单组任务适合研究状态提示，多组依赖任务才提供重叠结构的检验机会。

### 3.4 已有轨迹足以提出问题，重复实验决定效应是否稳定

多数任务目前只有 1–2 个 seed，每个设置运行一次。环境 seed 固定了场景，LLM 输出仍有随机波动。

后续需要在固定任务分布上重复运行，估计逐 task-seed 的结果差异及过程指标波动。版本和观察窗口应分层分析：v2 使用旧实现，v3/v4 使用相同运行代码，但灭火分别采用不同 seed 与 15/30 步窗口。

此前 ORCH/CAMON 的短实验用于分析各自执行链路；若研究架构差异，需要为它们接入同一套动作后状态与过程评价。

## 4. 可迁移部分与需要重做的部分

目前最具复用价值的是状态与事件接口：session、版本、事实来源、claim/observation 分离、投递反馈，以及动作和后置状态的关联。这些机制直接服务于前述闭环分析。

迁移时需要重做三个部分：

**观测映射。** CREW 地图来自共享累积缓存，每格最后观察时间未知。新环境应明确事实来源、更新条件和有效期，再决定哪些事实可以进入 context。

**组织依据。** 空间近邻适用于有位置意义的任务；代码或文档协作需要以权限、技能、资源持有和依赖关系替代空间距离。可替换的 policy 接口能够保留，分组规则需要随任务重建。

**执行与交接。** 当前接入围绕 Embodied 的逐步循环。长动作队列、异步工具和切组取消需要额外处理。receiver-side commit 则依赖资源身份、接收者与动作结果的可观测性。

因此，迁移工作的核心不是复制 prompt，而是建立新环境中“事实何时有效、依赖如何形成、完成怎样确认”的映射。

## 5. 用参考文档的指标推进研究

现有日志已覆盖状态、通信、动作和原任务结果。最先补齐的过程指标应直接对应上述四项现象。

| 研究问题 | 优先指标 | 定义重点 |
|---|---|---|
| agent 是否正确使用事实？ | runtime contradiction rate、错误持续时间 | 分开标注事实、意图和预测；将断言对齐到有效期内的环境证据 |
| 证据是否推动了行动？ | coordination lag、预算内未响应率 | 分解证据、提醒、相关动作、后置确认；包含未响应与超时 |
| 任务停在哪个环节？ | verified progress、阶段 dwell | 用环境证据定义完成；有可信阶段定义时计算 VMCR 与转换 precision/recall |
| 通信节约是否转化为总收益？ | 任务结果—token—时间联合比较 | 拆分调用成本，保留失败轨迹，检查运行轮数和历史增长 |
| 路由抑制了什么？ | false suppression 审计、消息后响应率 | 核对关键内容的可达性与采用；通过干预识别消息贡献 |
| 超边及重叠贡献了什么？ | ECV、Overlap Utility、跨边竞争 | 对成员、leader、重叠分别干预，匹配事实与预算 |
| 重组是否响应了任务变化？ | 事件校正 churn、重组延迟 | 将触发事件、任务依赖变化与实际重组关联 |

这里的测量单位决定解释。例如“已送达”衡量链路，“被采用”衡量响应，“环境确认完成”衡量任务推进。将这些单位分开，才能定位收益与失败发生的位置。

## 6. 下一步：围绕一个机制完成证据链

最值得优先推进的主问题是：

> 结构化协作状态是否减少错误完成声明，并缩短证据出现到正确行动的时间？

它可以利用已有的卸载、补水与救援轨迹，且同时覆盖成功恢复和持续停滞。研究步骤为：

1. 定义关键事实、完成声明、相关动作及后置条件，建立带事件编号的标注样本。
2. 比较原始 agent、同事实非超图共享、超图局部状态三组，分离事实供给与组织方式。
3. 在固定的新任务与 seed 上重复运行，测量矛盾率、错误持续时间、响应延迟和任务结果。
4. 定位局部状态产生收益或退化的环节，再开展 leader、成员与重叠结构干预。
5. 选择依赖结构不同的环境迁移，检查同一条证据—行动链是否仍能解释结果。

阶段 contract 和 guard 可以作为后续独立机制加入，用来研究可行性检查与恢复。其任务知识应明确提供给比较组，使结果对应到具体机制。

## 7. 研究结论

现有轨迹形成了四项连贯结论：

1. 正确记录世界状态与正确使用状态，是协作系统中的两个独立环节。
2. 消息减少与任务效率之间，需要通过信息采用、执行轮数和调用成本建立解释。
3. 协调停滞可以发生在信息送达之后，也可以发生在抵达目标之后；分段过程指标能够区分它们。
4. 活动量与原始评分需要连接到实际后置条件和任务代价，才能解释方法差异。

这些结论将超图研究具体化为一个可检验的问题：**局部组织能否让关键证据更及时地被采用，并推动可确认的任务进展。** 状态共享、路由、leader 和重叠成员的贡献，都可以围绕这一问题逐项识别。
